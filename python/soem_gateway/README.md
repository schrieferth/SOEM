# SOEM Python Gateway

This gateway exposes a small HTTP API around SOEM sample executables. It does
not import or link SOEM into Python. Instead it starts the external `simple_ng`
master sample and uses `slaveinfo` for adapter and inventory checks.

This is an integration layer for automation systems such as Testknecht. It is
not yet a deterministic native process-data gateway. It does, however, accept
the reduced runtime configuration generated by Testknecht and exposes the
server-side contract for catalog-backed paths, safe-off and subscriptions.

## Start

```sh
python3 python/soem_gateway/soem_gateway.py --interface en6 --port 8765
```

On macOS, EtherCAT/BPF access normally requires root privileges. Use the sudo
flags only when the selected operation needs real EtherCAT traffic:

```sh
python3 python/soem_gateway/soem_gateway.py \
  --interface en6 \
  --inventory-with-sudo \
  --start-with-sudo
```

Health, status and adapter discovery do not require root access. Inventory and
master start requests return `FAIL` with the captured SOEM output when the
external executable cannot open BPF, for example when it is not started through
`sudo`.

## Endpoints

- `GET /health`: gateway process health.
- `GET /status`: current master process state and log tail.
- `GET /adapters`: adapter list from `slaveinfo` without an interface.
- `GET /inventory?interface=en6`: one-shot `slaveinfo` inventory.
- `GET /logs`: master process log tail.
- `POST /start?interface=en6`: start `simple_ng` as master process.
- `POST /stop`: stop the master process.

The Testknecht-facing EtherCAT namespace is also available:

- `GET /ethercat/health`
- `GET /ethercat/status`
- `GET /ethercat/inventory`
- `POST /ethercat/request-config`
- `GET /ethercat/catalog`
- `GET /ethercat/read?path=<normalized-path>`
- `POST /ethercat/read-many`
- `POST /ethercat/write`
- `GET /ethercat/snapshot`
- `POST /ethercat/safe-off`
- `GET /ethercat/master/status`
- `POST /ethercat/master/start`
- `POST /ethercat/master/pause`
- `POST /ethercat/master/stop`
- `GET /ethercat/master/log`
- `POST /ethercat/subscriptions`
- `GET /ethercat/subscriptions`
- `GET /ethercat/events?subscription=<id>`
- `GET /ethercat/events/stream?subscription=<id>`
- `POST /ethercat/subscriptions/<id>/cancel`

## Runtime Configuration

The gateway does not parse ESI XML files. Testknecht reads the local catalog,
matches it with the live inventory and sends only the reduced runtime
configuration:

```json
{
  "interface": "en7",
  "catalog": {
    "parameters": [
      {
        "path": "ethercat.slot_2.el2004.output",
        "access": "write",
        "value_type": "bool",
        "safe_value": false
      },
      {
        "path": "ethercat.slot_3.el1014.input",
        "access": "read",
        "value_type": "bool"
      }
    ]
  }
}
```

`POST /ethercat/request-config` stores that configuration and resets the
gateway subscription/event state. Reads and writes are accepted only for paths
that exist in the loaded runtime configuration. `POST /ethercat/safe-off`
applies the configured `safe_value` to every writable path.

The current implementation keeps a cached process image in Python. That makes
the API contract testable and usable for moderate-rate evidence collection, but
a later native helper should own hard real-time process-data exchange,
watchdogs and high-rate event capture.

## Subscriptions

Clients can subscribe to value changes for one or more configured paths:

```json
{
  "paths": ["ethercat.slot_3.el1014.input"],
  "mode": "change",
  "deadband": 0,
  "min_interval_s": 0
}
```

Each emitted event contains the normalized path, old value, new value,
timestamp, quality, reason, subscription id and current master status. The
first implementation exposes a pollable event queue and a finite
Server-Sent-Events response for report/evidence collection.

## Boundary

The gateway keeps SOEM as an external executable boundary. That is useful for
systems that must not link SOEM directly into their own runtime. A later
dedicated C gateway can replace `simple_ng` when stable process-data read/write
operations are required. A pySOEM-based gateway can also implement the same
HTTP contract as a separate server process; Testknecht and Signalzwerg must not
import it directly.
